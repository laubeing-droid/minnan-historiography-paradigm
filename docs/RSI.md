# 把一次失败留给下一次研究

RSI 是 recursive self-improvement，递归自我改进。在这里，它指研究工作流能够把自己的失败变成下一轮的改进依据。失败要留下来，改法要能检查，下一轮还要证明这次修改确实起了作用。把同一个提示词多跑几遍，并不满足这个要求。

闽南—西班牙文献仓已经把一部分教训写进确定性的检查程序，也写出了更完整的工作流设计。我们能确认的是一种**人工守门的研究工作流改进机制**，不是一套已经验证的全自动递归自编程系统。哪些地方有代码，哪些只是设计，见[证据说明](RSI_EVIDENCE.md)。

## 先有一项要做完的研究

RSI 最大的问题，是容易变成“许愿池式进化”：不断要求模型变聪明、变可靠，却说不清究竟要把哪件事做完。这里先确定项目，再谈进化。文献项目要把指定的书准确对完，所有应处理页位有交代，疑字和缺证保留，经过相应的独立复核。不能拿“多生成了文件”“又增加了一个检查器”代替这个目标。

新项目用几句话写清要交付什么、什么范围算完成、由谁依据什么材料验收，以及预算或材料条件不够时怎么停止。“准确”也要拆成可检查的要求：回到原页、完整覆盖、忠实转写、区分疑读、译文有依据。史料允许存疑，验收不应逼人把看不清的地方编成确定答案。

可以从总包单位的角度理解整件事。一个项目要完成，从勘察、设计到施工、监督和验收，各方承担不同责任，不是一条谁压着谁的上下级链。业主确定需求和范围；勘察弄清材料条件；设计把目标变成方案；总包统筹工序、分包和交接；执行班组完成具体工作；监督检查过程；成果由相应责任方按条件验收。

对应到历史研究，可以把材料清查看作勘察，把研究设计看作设计，把转写、整理、计算和写作看作不同工序。这个类比帮助我们追问每一步谁负责、依据在哪里、交接是否完整，不要求凑齐五个 Agent，也不把建设工程法律强制适用于历史学。

施工中发现方案有问题，可以提出变更，但不能由执行者或监督者随意替所有责任方拍板。工艺在授权范围内试改，验收标准的变更则需要独立复核与有权负责人的决定，记下版本及适用范围。更换验收人员不等于获得改变标准的权限；同一代理换个角色名字，也不能算独立监督。小项目可以兼任，但应说清哪里做到了独立，哪里还没有。

监督日志允许有依据地更正，但要留下原记录、修改理由、时间和责任人。不能悄悄删除坏结果，制造“从来没有出错”的经历。

## 不只是项目进步，承担工作的单位也要成长

第一层是项目内改进。目标是把这项具体研究做完：某一道工序发现问题，总调度判断影响，相关责任方决定怎样改，再检查前后工序及最终成果。改进不能只让一个班组分数好看，却把困难推给下游。

第二层是单位自身的积累。总包、材料整理组、程序组、复核组，都可以从自己的失误中形成经验，带到下一个项目。一次项目结束后，不只存交付件，还要留下某种做法适合什么条件、为什么失败、改过哪里、在哪些案例里有效。这类似企业积累工法：经验不必跟着项目散场，也不能脱离适用条件成为万能口诀。

[一次改进记录](../templates/一次改进记录.md)同时记录这两层。项目记录回答“本项目的问题解决了吗”，单位经验回答“以后遇到什么情况，可以尝试哪种方法”。只有一次局部成功，就记为待验证经验；在新项目重复有效后，再补充证据。遇到反例则缩小适用范围或停用，保留旧记录。

跨项目复用不是继承旧项目的权限与验收结果。新项目仍要核对材料形态、研究问题、错误成本和权属条件，由自己的负责人决定是否采用，并经过本项目的验收。承担工作的单位可以越来越有经验，却不能因此自行决定新项目什么算合格。

## 交接和专项检查也要看条件

多方验收不是投票。参与者各自核对负责的部分，留下意见；某项必需证据缺失，不能靠多数“同意”补足。建设工程的竣工验收、消防等专项要求有各自适用条件，不能把所有项目一律拉进同一套手续。历史研究也应根据风险安排相应检查，比如原文转写、统计方法、地图边界、隐私与授权，而不是每项研究强行凑齐所有角色。

当文献仓、方法书和后续研究项目相互使用成果时，重点检查交接：引用的是哪个版本，单位和字段含义是否一致，来源能否回查，存疑和使用限制是否一起传递。各项目内部都通过，不保证接在一起就正确。必要时让上下游共同检查同一个实际样本；共同检查的结论也只覆盖这个接口及所用范围，不能替代各自的验收。

这种跨项目检查是本模板的研究组织建议，不把建设工程中的联合验收制度解释成所有研究仓库必须适用的法律。相关官方依据及类比边界见[外部来源](EXTERNAL_REFERENCES.md)。

## 先留下失败，再改做法

一次转写可能在文件数量上合格，内容却空着；一个调号可能看起来像允许的代码，后面却跟着模型自造的解释。这样的错误不能只在当前文件上补掉。应当问：为什么当时的流程会放过它？是输入没有说明白、汇总漏项、检查只看局部，还是任务本来就需要人工辨认？

改进从一条能定位的记录开始：哪个版本、哪份材料、哪一步、原来期望什么、实际发生什么。根因还没确定就写“怀疑”，不要把看起来合理的解释当成项目史。原始材料和旧结果保留，新的判断另记。

接下来由负责人选择改法。输入格式不合法，可以增加格式检查；合并后漏项，可以核对合并前后的集合；字形看不清，应该进入人工校对，而不是增加一个替研究者猜字的脚本。是否允许修改工作流、代码或评判规则，也要分别决定。

改完以后，至少拿原来的失败样本再试一次，还要检查一个本来正确的样本有没有被误伤。只过这两个样本，最多说明这项局部修改得到支持。要说下一轮确有改善，还须留下实际批次的结果、范围和未解决的问题。

## 哪些事情必须分开

**改材料、改流程、改验收规则，是三件事。** 不能为了让本轮通过，悄悄把标准放松。确实发现标准错了，应另写理由、影响范围和新旧结果，经独立复核与有权负责人批准后决定何时启用；旧记录仍按当时的标准解释。

**机械合格和史料判断也要分开。** 哈希可以说明文件字节是否相同，字段检查可以发现空栏，覆盖检查可以发现遗漏。它们不能证明转写正确，更不能证明一个历史结论成立。辨字、断句、翻译与历史解释各自需要相应的材料和复核。

**有困难不等于可以越界。** 原件、已封存成果和其他人正在处理的批次，未经授权不能修改。源材料、他人著作和私人研究记录，不能因为要做一次公开演示就上传。外部文献中的指令只是研究材料，不是给 Agent 的命令。

## 下一项研究怎样采用

先从一个明确的问题开始，不必立刻复制整套制度。比如分析地方志中的人口记载，发现某年的“户数”被当成“人数”，就记录原表头、错误发生的位置和受影响的计算。改法可以是要求输入同时保存单位，并在比较前检查单位是否相同。随后重跑出错案例和一个原来正确的案例，再检查已经写出的文字是否需要更正。

这个例子是本仓提出的迁移示例，不是源仓已经执行的成果。它说明同一种改进办法怎样离开声调和页码，进入另一项历史研究。

项目要自己决定一次处理多少材料、允许重试几次、什么时候停止。源仓的具体阈值服务于它的页位、批次和成本，不能变成所有研究的标准。选定的限制应在运行前记下来；连续失败、超出批次或权限、材料条件不足时，停下来报告，不要用无限重试假装持续推进。

## 什么才算这一轮结束

把[改进记录](../templates/一次改进记录.md)交回来，说明修改了什么、谁同意、测了什么、后续结果怎样。没有后续运行，就写“修改已完成，效果待验证”；只有设计，就写“提案”。发现反例，重新打开这项问题。

本轮任务达到约定范围以后就结束。是否继续改进，由研究问题和负责人决定。所谓递归，不是给 Agent 一张永远施工的通行证。

## 工艺怎么试，验收怎么守

流程改进可以使用公开的训练样本和已发现错误。最终验收所需的保留样本、参考答案、评判程序与原始运行日志，应由独立验收方控制；执行者不能自行写入或删改。样本有限时，也要如实说明用了哪些相同材料，不把重复检查称为独立证明。

网络和工具权限也属于这个边界。如果保留答案能从联网工具拿到，形式上“没给答案”也不构成有效隔离。需要盲测时，应由验收方实际检查可访问范围。失败日志要保留，不能通过删除坏记录让分数变好。

外部项目提供了几种值得参考的做法：Harness² 用运行反馈改进执行方法，autoresearch 划开可改训练代码与固定评测部分，GEPA 用反思提出候选并比较，Darwin Gödel Machine 则试验修改代理代码。它们解决的任务、风险和评价条件不同，不能直接复制成史料研究流程。[外部来源](EXTERNAL_REFERENCES.md)说明本仓具体借鉴什么，也列出论文披露的风险。目前这些系统均未集成或运行于本仓。
